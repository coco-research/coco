# brownfield_map.py fixtures

Generated by `make_fixtures.py` into `_build/` (gitignored, regenerated on demand).
Three repositories: `map-written` (two commits, a helper, a caller and a test),
`greenfield` (one commit, one file), and `repo-root-mismatch` (one commit, plus
a nested, unrelated one-commit repository, `nested-unrelated`, that has no
`.team-ship` of its own). The self-test reuses `map-written` for most of its
cases (`map-with-task`, `binary-absent`, `ripwire-fails`, `no-run`,
`repo-root-subdir`, and `real-binary` when a binary is present); only the
environment, or the `--repo-root` argument, changes between them.

## The repo-root mismatch rule

`--repo-root` may be any subdirectory of the repository the active run
belongs to: `gate_state.find_run()` walks up from it to the same
`.team-ship/RUN` pointer regardless of how deep the argument sits. Before
`brownfield_map.py` writes or appends anything, it checks the git repository
containing `--repo-root` (`git -C <argument> rev-parse --show-toplevel`)
against `run.json`'s own `repo_root`. When they agree, everything from then
on, including where the artifacts land, uses the recorded `repo_root`, never
the raw argument. When they differ, `--repo-root` is inside a different
repository than the one the found run belongs to, most dangerously a nested,
unrelated repository sitting a few directories below (or beside) the run's
own root, whose presence `find_run()`'s walk-up cannot distinguish from an
ordinary subdirectory. Left unchecked, that silently corrupts a healthy run:
the wrapper would exit 0 having written both artifacts and their receipts
into the nested repository's own `.team-ship`, tagged with the nested HEAD,
while appending receipts into the outer run that claim the files live under
the outer root. The check refuses this before anything is written, with one
stderr line naming both directories.

- `repo-root-mismatch`: proves the refusal. `--repo-root` points at
  `nested-unrelated` inside the `repo-root-mismatch` fixture, which has its
  own run. Exit 2, the one stderr line names both the nested and the outer
  directory, `nested-unrelated/.team-ship` is never created, the outer run's
  own `.team-ship` still holds only `RUN`, and `gate_state.py verify-chain`
  in the outer repository still exits 0 against the receipt the self-test
  seeds before the mismatched call, because that call appends nothing.
- `repo-root-subdir`: proves the recorded root wins even for an ordinary,
  same-repository subdirectory. `--repo-root` points at `map-written`'s own
  `src/`, which has no repository of its own, so `rev-parse --show-toplevel`
  agrees with the recorded root. Exit 0, and the artifacts land under the
  repository root, `.team-ship/`, never under `src/.team-ship/`.

## The stub

`stub-ripwire` is a small Python script that stands in for the real, installed
binary. `--self-test` copies it onto a temporary directory as a file literally
named `ripwire` and prepends that directory to `PATH`, which is how
`brownfield_map.py`'s own PATH-based resolution finds it. It does not read the
repository it is pointed at; it prints one of two fixed, redacted JSON documents
(the shape of a real `ripwire <dir> --json` run and a real
`ripwire <dir> --json --for=TASK` run, both taken from the installed 0.6.1
binary against a two-file, one-test throwaway repository) and echoes the real
`root` and `task` arguments into it. Setting `RIPWIRE_STUB_FAIL` makes it print
one stderr line and exit 3 instead, for the `ripwire-fails` case. It honours
`--version`.

Because the stub's JSON never reflects the real fixture repository, greenfield
detection in `brownfield_map.py` is computed straight from `git` (commit count
and tracked file count), never from ripwire's output. That is also why the
`greenfield` fixture only needs one real commit and one real tracked file: the
self-test checks that the word "greenfield" appears in the rendered Summary,
which comes from the git facts, not from the stub's canned symbol count.

## Self-test cases

- `map-written`: `map-written` fixture, stub on `PATH`, no `--for`. Exit 0, both
  `.team-ship/brownfield-map.json` and `.team-ship/BROWNFIELD-MAP.md` present,
  all five headings present, and `gate_state.py verify-chain` exits 0 in the run
  directory afterward.
- `map-with-task`: same fixture and stub, `--for "fix the add helper"`. Exit 0,
  the task text appears in the rendered Summary, and the Impact section is not
  empty.
- `binary-absent`: `PATH` restricted to `/usr/bin:/bin`, `RIPWIRE_BIN` unset, and
  `HOME` pointed at an empty temporary directory so the real
  `~/.local/bin/ripwire` installed on the machine this suite runs on cannot leak
  in. Exit 2, naming `RIPWIRE_BIN`, `PATH` and `~/.local/bin/ripwire` in the one
  stderr line.
- `ripwire-fails`: stub on `PATH` with `RIPWIRE_STUB_FAIL=1`. Exit 2, with the
  stub's own stderr line, "ripwire: stub forced failure for fixture testing",
  present in `brownfield_map.py`'s stderr.
- `no-run`: `map-written` fixture copied without `gate_state.start_run()`, so
  `.team-ship/RUN` never exists. Exit 2.
- `greenfield`: `greenfield` fixture, stub on `PATH`. Exit 0, and the rendered
  Summary states the repository is greenfield.
- `repo-root-mismatch` and `repo-root-subdir`: see "The repo-root mismatch
  rule" above.
- `real-binary`: the one permitted skip in this suite. If a real ripwire binary
  resolves through `brownfield_map.py`'s own resolution order (which, absent
  `--self-test`'s environment overrides, is however this machine is actually
  configured), it is pointed at through `RIPWIRE_BIN` and run once against
  `map-written` for a real exit-0 check. If none resolves, this case prints
  "real-binary: skipped, no binary" and is not counted as a failure. CI has no
  binary, so this case always skips there; that is the intended, documented
  gap.

## Why Impact without a task ranks by importance, not churn

`ripwire --json` does not carry a per-file churn number outside of
`--hotspots`, and running the installed 0.6.1 binary confirms `--hotspots`
refuses `--json` outright:

```
$ ripwire . --hotspots --json
ripwire: --json is not yet supported for --hotspots -- supported: the default
map, --for, --pack-task, --callers/--callees, --impact, --quality-delta,
--test-gate, --metrics, and --plan-lanes which is JSON-native (e.g.
ripwire <dir> --callers=SYM --json)
```

`brownfield_map.py` makes exactly one ripwire call, so it cannot fall back to a
second, XML-only `--hotspots` call without breaking that contract. Without a
task, its Impact section instead ranks files by the same call-graph importance
score (`k`) the default map already carries in its `r` array, and says so in
the rendered text, rather than mislabeling that score as churn. With a task,
`--for=TASK`'s `sigs` entries do carry a real per-symbol `churn` field, so
Impact there is the task's own ranked symbols and files, exactly as
`ripwire --help` describes `--for`: "the task lens: say what you are doing,
get the signatures and bodies to read first."

## Flags relied on

- `--json`: "emit JSON instead of XML; keys mirror the XML attribute names one
  to one" (`ripwire --help`). Confirmed against the installed 0.6.1 binary on a
  small throwaway repository: the default map's top level carries `files`,
  `symbols`, `edges`, `order`, `root`, `pr_iters` and an `r` array of
  `{p, s: [{t, n, k, c}]}`; `--for`'s top level carries `task`, `route`,
  `confidence`, `kept`, `scored`, `corpus`, `bundle` and a `sigs` array of
  `{l, n, p, cx, ccx, in, churn, amp, tested, r, sig}`. A file entry in `r`, or
  a symbol entry in `sigs`, carries `"layer": "test"` when ripwire classifies
  it as a test.
- `--for=TASK`: "the task lens: say what you are doing, get the signatures and
  bodies to read first" (`ripwire --help`).
- `--version`: prints the binary's version line; used to populate
  `ripwire_version` in `gates/handoff-1-map.json`.
