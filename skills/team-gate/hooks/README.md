# team-gate hooks

Four Node hooks, no dependencies, that certify what the `/team:*` gates
already measure. A hook is the only component the model cannot skip,
because the harness runs it around every tool call. The scripts under
`skills/team-gate/scripts/` measure; these hooks certify.

## Registration: install.py, not a tracked settings.json

This repository's `.gitignore` excludes `.claude/` on purpose (IDE-local
config, wired per machine through installers under `adapters/*/install.sh`,
never committed). A `.claude/settings.json` in this repository is
therefore always local, generated state, never the tracked artefact.

`install.py` in this directory is the tracked artefact. It merges the
four hook registrations into a settings file rather than shipping one:

```
python3 skills/team-gate/hooks/install.py --project <repo-or-worktree-dir>
python3 skills/team-gate/hooks/install.py --user
python3 skills/team-gate/hooks/install.py --project <dir> --check
python3 skills/team-gate/hooks/install.py --project <dir> --remove
```

`--project DIR` writes `DIR/.claude/settings.json`. When the target project
contains `skills/team-gate/hooks/`, it writes commands of the form
`node "$CLAUDE_PROJECT_DIR/skills/team-gate/hooks/<name>.js"` (works for the
coco repository itself). For consumer repositories without that directory,
it writes the absolute path form `node "<absolute path>/<name>.js"` instead.
`--user` writes `~/.claude/settings.json` with the absolute path of each
hook file, since `$CLAUDE_PROJECT_DIR` has no meaning at user scope. The merge
only ever appends entries for the four hooks that are not already present
(detected by the hook's filename appearing in an existing command string), so
a second run changes nothing and every other hook or setting in the file is left
untouched. Before the first time it ever modifies a given file, it writes
`<file>.bak-team-gate`, a plain byte copy with no timestamp; that backup is never
overwritten by a later run. `--remove` strips exactly the entries naming one of
the four hook files, leaving unrelated hooks and settings (including that backup)
alone. `--check` exits 0 when all four are registered and the referenced hook
files exist, and 1 otherwise.

The worktree's own `.claude/settings.json` used for the observed pilot
run in this project is exactly this: local activation state generated by
`install.py`, correctly ignored by git, not something to hand-edit or
commit.

## Mode switch: observe, then enforce

Every run's `run.json` carries a `flags` list (for example
`["hooks=enforce"]`), written once by `gate_state.py start <repo>
<command> hooks=enforce`. Each hook reads it and defaults to `observe`
when the flag is absent. In **observe** mode a hook computes exactly the
decision it would enforce, records it in the `certified` receipt as
`would-deny` (PreToolUse) or `would-block` (Stop), and writes nothing to
stdout, so the model's turn is never affected. In **enforce** mode it
writes the deny or block JSON in the forms below. Nothing else differs
between the two modes: the receipts from an observed run are the proof
that enforcement will behave the same way.

- PreToolUse deny: `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "<reason>"}}`
- Stop block: `{"decision": "block", "reason": "<reason>"}`

## Substrate facts these hooks rest on (PLAN.md section 2 and section 4)

- The harness fails open on a hook timeout: the hook is killed and the
  tool call proceeds. No hook here does anything but cheap, local work
  (file reads, JSON parses, one subprocess call to a wave-two script),
  and every registration in `.claude/settings.json` carries a 60-second
  timeout so a slow disk does not turn into an accidental fail-open.
- Hooks fire in every permission mode, including for subagent tool
  calls, which carry `agent_id` and `agent_type`.
- The hook payload carries `session_id`, `tool_use_id`, `agent_id`,
  `agent_type`, `permission_mode`, `transcript_path`, `cwd`, `tool_name`,
  `tool_input` (for Bash, `tool_input.command`; for Write and Edit,
  `tool_input.file_path`), and on PostToolUse `tool_response`, which for
  Bash has no exit code. `UserPromptSubmit` carries the raw `prompt`.
  `Stop` carries `background_tasks` and `last_assistant_message`, plus
  `stop_hook_active` (false on the first fire, true on re-entry).
- Because a killed PreToolUse hook still lets the tool call proceed, the
  design is fail-closed at the run level, not at the call level: every
  gating PreToolUse decision appends a `certified` receipt keyed by
  `tool_use_id`, and the paired PostToolUse hook appends a `gate-timeout`
  receipt (which the aggregators treat as blocking) whenever that
  certification is missing for a call it should have gated.

## Shared library

`lib.js` resolves the active run by walking up from `payload.cwd` for
`.team-ship/RUN`, exactly as `gate_state.find_run` does, and returns the
directory that held the marker (the repository root) alongside the run
directory under `TEAM_STATE_ROOT` (default `~/.team/runs`). It is the
only place that shells out to `gate_state.py`, `ship_gate.py` and
`check_artifacts.py`, so there is exactly one writer of `receipts.jsonl`
and one path resolution for the wave-two scripts.

Every hook reads all of stdin synchronously (`fs.readFileSync(0)`, no
timer, no early exit on slow input), wraps its body in a try block, and
never throws to the harness: on any error after a run is found, it
appends a `block` receipt with the error text and always exits 0. A hook
that cannot even parse its payload, or cannot resolve a run from
`payload.cwd`, exits 0 silently with no receipt: there is nothing to
certify and no run to attach a block to.

One deliberate narrowing: if a run is found but `run.json` itself cannot
be read or parsed (a genuinely unspecified, unfixtured corruption), the
hook cannot determine whether it is in enforce mode, so it stays silent
rather than guessing enforce and denying. It still writes a `block`
receipt when the run directory is writable, which is what makes the
run fail closed at aggregation (`ship_gate.py check` and the Stop guard
both treat any `block` receipt as blocking) even though this one call
was not stopped in the moment.

## team-turn-log.js (UserPromptSubmit)

Approval provenance. When a run is active and the raw prompt matches the
approval pattern (case-insensitive, matched on the whole trimmed prompt
or as a leading phrase: "approve", "approved", "approve the plan",
"proceed", "go ahead", "ship it", "lgtm", "yes, proceed"), appends an
`approval` receipt with `{text, sha256, stage: "approval"}`. A prompt
beginning `override <gate>: <text>` appends an `override` receipt with
`{gate, instruction, by: "user"}`. This hook never denies and never
writes to stdout, in either mode; the mode switch above does not apply
to it.

## team-artifact-guard.js (PreToolUse and PostToolUse, Write, Edit, MultiEdit)

Stage order and evidence protection. `.team-ship/EVIDENCE.json`,
`.team-ship/EVIDENCE.md`, anything under `.team-ship/gates/`, and
anything resolving into the run directory are always denied: those are
written only by team-gate scripts through Python's own file I/O, never
through the model's Write tool. There is no exemption, matching PLAN.md
section 4.

Any other write under `.team-ship/` is mapped to a stage by searching
every numeric key in `ship-manifest.json` for one whose `outputs` list
names the write's repo-relative path. `PLAN.md` is declared by both
stage 3 (Plan) and stage 5 (Fix Plan); the ambiguity is resolved by
querying `ship_gate.py stage <n>` for each candidate in ascending order
and taking the first one that is already allowed, falling back to the
smallest candidate's (failing) result otherwise, since that is the next
stage the model has not yet completed. A path under `.team-ship/` that
is not a declared output of any stage is ungoverned and silent.

`ship_gate.py stage <n>` exit 0 is allow; exit 1 is deny with the query's
own `reason` field (naming the missing or failing gate file); exit 2 is
deny with "cannot measure stage preconditions". The certified receipt
records `guard` ("always-deny" or "stage"), and for the stage case, the
resolved `stage` number, so the paired PostToolUse call does not have to
re-run the manifest lookup.

On PostToolUse, the certified receipt is looked up by `tool_use_id`;
absent means `gate-timeout`. For the "always-deny" class there is
nothing further to record. For the "stage" class, an `artifact-written`
receipt (`path`, `sha256`, a raw line count, `stage`) is appended, a
`stage-opened` receipt is appended the first time an artifact of that
stage is written in the run, and `check_artifacts.py stage-output <n>
<path>` validates the artifact's own content (minimum lines, required
headings, forbidden tokens). `check_artifacts.py` also appends its own
`artifact-written` receipt on success, using its own non-trivial-line
count; the two receipts are deliberately redundant, not contradictory
(latest-wins path verification tolerates either). A non-zero exit from
`stage-output` appends a `block` receipt naming the stderr reason; the
file is already on disk, so the run is blocked at aggregation rather
than the write being undone.

## team-stage-guard.js (PreToolUse and PostToolUse, Bash, Agent)

The PR gate and the spawn gates. A Bash command is gated only when,
after skipping any leading `NAME=value` env prefix, its first words are
exactly `git push`, `gh pr create` or `gh pr merge`; every other Bash
call is silent. The persistent effect being gated is exactly those three
commands, not every `gh pr` subcommand. A gated call runs `ship_gate.py
check --repo-root <repo>`: exit 0 is allow, exit 1 is deny with the
first non-empty stderr line, exit 2 is deny with "cannot measure" (which
is what a run with no receipts at all produces, since an empty chain is
UNRUNNABLE to `ship_gate.py`, not BLOCK).

Every Agent spawn appends an `agent-spawned` receipt
(`description`, `subagent_type`, `model`). When the description or
prompt contains "build" or "implement", it is additionally gated on
`ship_gate.py stage 6`; any non-zero exit there denies with a reason
naming that Layer 2 build work was spawned before stage 6 is reachable.
Every Agent spawn, gated or not, gets a certified receipt.

On PostToolUse, a gated Bash or Agent call without a certified receipt
appends `gate-timeout`. A `gh pr create` that has a certified receipt
has its stdout scanned for a `https://github.com/.../pull/<n>` URL,
which is recorded as `pr-opened`. An Agent PostToolUse call appends
`agent-returned`.

## team-stop-guard.js (Stop)

A run may not end silently mid-pipeline. `stop_hook_active: true` always
allows (this is what stops the model being trapped in a loop across
re-entries); a non-empty `background_tasks` list always allows. Failing
those, a `block` or `gate-timeout` receipt already in the chain blocks
once with that receipt's own reason. Otherwise, unless a `pr-opened`
receipt exists or the highest `stage-opened` receipt is stage 14 or
above, the run is in flight: the decision is block, naming the current
stage and the remaining stages from a pure, side-effect-free
`ship_gate.py stage 14` query (never `ship_gate.py check`, which writes
`gates/14.json` on every call). A `stop-checked` receipt recording the
decision and reason is appended on every path, including the allow
paths.

## Testing

`skills/team-gate/scripts/hooks_selftest.py` (stdlib only) builds a real
git repository plus a temporary `TEAM_STATE_ROOT` and run for every case,
feeds the fixture payload from `fixtures/<hook>/<case>.json` to `node
<hook>` with `cwd` set to the fixture repository, and asserts stdout,
exit code and the receipts appended. Deep gate state for stages 7 to 12
is hand-fabricated the same way `ship_gate.py`'s own `--self-test`
fixtures are (a JSON gate file plus a matching `gate-result` receipt
through `gate_state.py`'s own CLI), since `ship_gate.py`'s evaluation of
a gate file reads only its `head` and `exit` fields. Handoff gates
(stages 1 to 6) are produced by actually running `check_artifacts.py`
against real, valid artifact files. The same file also exercises
`install.py`: fresh install, idempotent second run, preserving an
unrelated hook and a `permissions` key with the backup verified byte for
byte, `--remove` leaving that unrelated hook in place, and `--check`
failing on a settings file that never had the four registered.

`run_fixtures.sh` (owned by another task in this project) is expected to
call this file the same way it calls every other wave-two script's
self-test.
