# Wave 4 brief: the four hooks, observe mode first (task 14), then the denies (tasks 16 to 18)

The scripts measure; the hooks certify. A hook is the only component the model cannot skip, because the harness runs it around every tool call. This brief specifies four Node hooks that live in the repository, are registered by the repository's own project settings, and start in observe mode: they write receipts describing what they would have denied and deny nothing. After one real pipeline has run under observation, the denies are switched on one at a time.

Substrate facts these hooks rest on, all verified on this machine on 2026-09-17 and recorded in PLAN.md section 2 and section 4. The harness fails open when a hook exceeds its timeout: the hook is killed and the tool call proceeds. Hooks fire in every permission mode and for subagent tool calls. The PreToolUse deny form is `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "<one line>"}}`. The Stop block form is `{"decision": "block", "reason": "<what remains>"}`, and `stop_hook_active` is false on the first fire and true on re-entry. The hook payload carries session_id, tool_use_id, agent_id, agent_type, permission_mode, transcript_path, cwd, tool_name, tool_input (for Bash, tool_input.command; for Write and Edit, tool_input.file_path), and on PostToolUse tool_response, which for Bash has no exit code. UserPromptSubmit carries the raw prompt. Stop carries background_tasks and last_assistant_message.

## Common rules for every hook

1. Location and registration. The hooks live at skills/team-gate/hooks/<name>.js and are registered in the repository's `.claude/settings.json` (create it if absent; it is a tracked file) under `hooks`, each entry `{"matcher": "<tools>", "hooks": [{"type": "command", "command": "node \"$CLAUDE_PROJECT_DIR/skills/team-gate/hooks/<name>.js\"", "timeout": 60}]}`. The owner's `~/.claude/settings.json` is not touched; the probe hook registered there during research is removed by the brain at the end of the project.
2. Node with no dependencies. Read all of stdin before parsing; no stdin timer, no early exit on slow input. Exit 0 with no stdout when there is nothing to say. Never throw to the harness: wrap the body in a try block that, on any error, writes a `block` receipt with the error text when a run is active and exits 0 in observe mode; in enforce mode a hook that cannot read its input or the state directory denies with the reason, because a hook that cannot measure must not certify.
3. Run resolution. Walk up from payload.cwd for `.team-ship/RUN`, read the run id, resolve `TEAM_STATE_ROOT` or `~/.team/runs`, and require the directory to exist; otherwise the hook is not in a run and exits 0 silently. Read run.json; its `flags` object carries `hooks: "observe" | "enforce"`, defaulting to observe when absent.
4. Receipts. Every receipt is appended by shelling out to `python3 <repo>/skills/team-gate/scripts/gate_state.py receipt <kind> '<json>' --hook-payload -` with the hook payload on stdin, so there is exactly one writer of receipts.jsonl and the lock and chain rules hold. The receipt library is resolved relative to the hook file (`../scripts/gate_state.py`). A non-zero exit from the receipt command is itself an error under rule 2.
5. Certification pairing. Every gating PreToolUse decision appends a `certified` receipt whose detail carries `hook`, `tool_use_id`, `decision` ("allow", "deny", or "would-deny" in observe mode) and `reason`. The paired PostToolUse hook, on the same matcher, looks up the certified receipt for its tool_use_id; when it is absent for a call the hook should have gated, it appends a `gate-timeout` receipt naming the tool_use_id and the command or path, which the aggregators treat as blocking. This is the fail-closed-at-run-level design PLAN.md section 4 describes.
6. Cheap work only. A PreToolUse hook reads files, parses JSON, compares hashes and HEAD, and may run `ship_gate.py stage <n>` or `ship_gate.py check`, both of which read state and run render_evidence --check; it never runs tests, never scans a repository, never spawns a model. Budget: every PreToolUse path completes in under five seconds on this machine; the settings timeout is 60 seconds so a slow disk does not turn into a fail-open.
7. Mode switch. In observe mode a hook computes the same decision it would enforce, records it as "would-deny" or "allow" in the certified receipt, and never writes a deny to stdout. In enforce mode it writes the deny. Nothing else differs, so the receipts from an observed run are the proof that enforcement will behave.
8. Testing. Each hook has fixtures under skills/team-gate/hooks/fixtures/<name>/: JSON payload files and expected outcomes. A Python runner skills/team-gate/scripts/hooks_selftest.py (stdlib, same conventions as every other script) creates a temporary run with gate_state, sets TEAM_STATE_ROOT and a temporary repository with a `.team-ship/RUN` pointer, feeds each payload to the hook through `node <hook> < payload` with cwd set appropriately, and asserts the stdout JSON, the exit code, and the receipts appended, one line per case in the existing format. run_fixtures.sh calls hooks_selftest.py.
9. No em dash, no section sign, no wall-clock in any receipt detail beyond what gate_state stamps.

## Hook 1: team-turn-log.js, UserPromptSubmit

Purpose: approval provenance. The approval gate between Stage 4 and Stage 5 requires the human's literal words. The hook reads the prompt; when a run is active and the prompt matches the approval pattern, it appends an `approval` receipt with detail `{text: <the raw prompt>, sha256: <sha256 of the raw prompt>, stage: "approval"}`. The approval pattern is a small explicit list, case-insensitive, matched on the whole trimmed prompt or on a leading phrase: "approve", "approved", "approve the plan", "proceed", "go ahead", "ship it", "lgtm", "yes, proceed". Anything else appends nothing. The hook never denies and never outputs. An `override` is also recognised here: a prompt beginning "override <gate name>:" followed by text appends an `override` receipt with detail `{gate, instruction: <the raw text after the colon>, by: "user"}`; that is how a human records a deliberate bypass in their own words, and ship_gate then reports PASS_WITH_OVERRIDE and the PR body carries the instruction verbatim.

Fixtures: approve-plain (appends approval), approve-with-noise ("Approved, go ahead with option B" appends approval), no-approval ("what is the status" appends nothing), override ("override coverage: pilot repository has no pytest, accepted by Rijul" appends override with gate "coverage"), no-run (a prompt with no active run appends nothing and exits 0).

## Hook 2: team-artifact-guard.js, PreToolUse and PostToolUse on Write|Edit|MultiEdit

Purpose: stage order and evidence protection. On PreToolUse, resolve tool_input.file_path; if it is not under `<repo>/.team-ship/` exit 0 silently. If it is `.team-ship/EVIDENCE.json`, `.team-ship/EVIDENCE.md`, anything under `.team-ship/gates/`, or anything under the run directory, the decision is deny with reason "evidence and gate files are written only by team-gate scripts"; there is no exemption, because scripts write with Python, not with the Write tool. Otherwise map the path to a stage through ship-manifest.json outputs (the artifact's stage is the stage whose outputs list names it; the approval artifacts belong to stage 5 through the approval key) and run `ship_gate.py stage <n> --repo-root <repo>`; exit 1 from that query is deny with the JSON reason's `reason` field; exit 2 is deny with "cannot measure stage preconditions" in enforce mode and would-deny in observe mode. Append the certified receipt with the decision. On PostToolUse for the same paths: look up the certified receipt; absent means gate-timeout. When the write succeeded and the path is a manifest output, append an `artifact-written` receipt with path, sha256 and line count, then run `check_artifacts.py stage-output <n> <path> --repo-root <repo>`; a non-zero exit appends a `block` receipt with the stderr reason (the file is already written; the aggregator blocks on the receipt). Also append a `stage-opened` receipt with `stage: n` the first time an artifact of stage n is written in the run, which is what derive_status counts.

Fixtures: write-evidence-md (deny or would-deny), write-stage-2-before-stage-1 (stage query 1, deny with the missing gate named), write-stage-2-allowed (allow, certified, then Post appends artifact-written, stage-opened and a passing stage-output), write-outside-team-ship (silent exit 0, no receipt), post-without-certified (gate-timeout receipt), post-failing-artifact (stage-output non-zero, block receipt).

## Hook 3: team-stage-guard.js, PreToolUse and PostToolUse on Bash|Agent

Purpose: the PR gate and the spawn gates. On PreToolUse Bash: if tool_input.command matches `gh pr create`, `gh pr merge`, or `git push` (tokenise with a shell-word regex; match the first two words after any env prefix), run `ship_gate.py check --repo-root <repo>`; exit 0 is allow, exit 1 is deny with the first failing row as the reason, exit 2 is deny with "cannot measure". Any other Bash command exits 0 silently with no receipt. On PostToolUse Bash for a `gh pr create` that was allowed: parse the PR URL from tool_response.stdout and append a `pr-opened` receipt with `url`. On PreToolUse Agent: append an `agent-spawned` receipt with `description`, `subagent_type`, and `model` from tool_input when present; when the description or prompt names Layer-2 build work (the prompt contains "build" or "implement" and the run's current stage is below 6 by `ship_gate.py stage 6`), the decision is deny with the stage reason; otherwise allow. On PostToolUse Agent: append `agent-returned` with the tool_use_id. Certified pairing applies to every gated Bash and Agent call.

Fixtures: pr-create-all-green (allow, certified, pr-opened on Post with the URL), pr-create-blocked (deny with the failing row), pr-create-unmeasurable (deny "cannot measure"), git-push-blocked, ordinary-bash (silent), agent-spawn-builder-before-stage-6 (deny), agent-spawn-researcher (allow with agent-spawned), post-agent (agent-returned).

## Hook 4: team-stop-guard.js, Stop

Purpose: the run may not end silently mid-pipeline. When a run is active, compute `derive_status` through `gate_state.py status` and read whether a `pr-opened` receipt exists. If the run is in flight (status not blocked, no pr-opened receipt, and the highest stage-opened is below 14), background_tasks is empty, and stop_hook_active is false, the decision is block with reason "run <id> is at stage <n>; remaining: <list of stages without a passing gate>; run ship_gate.py check or record an override". If stop_hook_active is true, allow, so the model is never trapped in a loop. If background_tasks is non-empty, allow. If the run is blocked by a block or gate-timeout receipt, block once with the receipt's reason. Always append a `stop-checked` receipt with the decision and the reason; in observe mode the decision is recorded as would-block and nothing is written to stdout.

Fixtures: in-flight-first-stop (block or would-block with the remaining list), in-flight-re-entry (stop_hook_active true, allow), background-tasks (allow), pr-opened (allow), no-run (silent exit 0).

## Task 14 delivery

Sonnet builder, one agent for all four hooks and the self-test runner, because they share the run-resolution and receipt helpers, which live in skills/team-gate/hooks/lib.js and are required by each hook. Deliverables: four hooks, lib.js, hooks_selftest.py, fixtures, the `.claude/settings.json` entries, and a README in skills/team-gate/hooks/ stating the mode switch and the substrate facts. Verification: a Sonnet round that runs every fixture through node, checks the deny and block JSON shapes byte for byte against the forms above, confirms every gated decision has a certified receipt and every missing certification produces a gate-timeout, confirms observe mode writes nothing to stdout, and confirms the settings file registers exactly the four hooks with timeout 60. Then the brain runs one real pipeline in observe mode on a fixture repository with the probe payloads and reads the receipts.

## Tasks 16 to 18: the denies, one at a time

Each is a one-line change of the run's hooks flag from observe to enforce for one hook, followed by a deliberate violation and the transcript showing the deny with its reason. Task 16: the PR gate (Bash `gh pr create` with a red gate is denied). Task 17: the Stop guard (ending a turn mid-pipeline is blocked once and allowed on re-entry). Task 18: artifact ordering and Agent spawns (writing the stage 3 plan before the stage 2 options is denied; spawning a builder before stage 6 is denied). The flag is per run and set by `gate_state.py start <repo> <command> hooks=enforce`, so an ordinary session on this machine is unaffected until a run asks for enforcement.
