# ship_gate.py fixtures

Each fixture under `_build/<name>/` is a tiny fixed-date git repository at
`repo/` plus a run directory at `state/<name>/`, generated by
`make_fixtures.py`. Regenerate with:

```
python3 make_fixtures.py            # writes to ./_build next to this file
python3 make_fixtures.py --out DIR  # writes elsewhere
```

Two generations to the same location are byte-identical except
`.git/index` and `.git/logs`, because `TEAM_FIXED_TS` (default
`2026-01-01T00:00:00Z`) pins every git commit's author and committer date
and every receipt's timestamp.

## Why the receipts are hand-rolled instead of calling gate_state.append_receipt

`gate_state.start_run()` derives `run_id` and `run.json`'s `started_at`
from `datetime.now()`, and `gate_state.append_receipt()` derives every
receipt's `timestamp` the same way. Neither can be made deterministic by
an environment variable, so calling them directly would make two
generations differ on every run. This generator instead reproduces their
exact record shape and hash algorithm by hand (same canonical-JSON
SHA-256 as `gate_state._sha256_json`), substituting `TEAM_FIXED_TS` for
the wall-clock reads. `gate_state.py`'s own fixtures
(`fixtures/gate_state/make_fixtures.py`) use the same technique for the
same reason. `verify_chain`, `derive_status`, and `ship_gate.py` itself
only read the structure; none of them cares whether a timestamp is real.

## Where the gate-file shapes came from

Every field name in `_handoff_data`, `_discover_data`, `_parity_data`,
`_run_data`, `_prove_red_data`, `_recheck_data`, `_coverage_data`,
`_verify_compare_data`, `_matrix_data`, and `_claim_check_data` in
`make_fixtures.py` was copied from one real run of the committed
check_artifacts.py, run_gate.py, prove_red.py, verify_independent.py and
claim_evidence.py against a temporary copy of
`fixtures/run_gate/_build/all-pass`, not guessed. That same real sequence
is what the `real-pipeline` case in `ship_gate.py --self-test` runs again
on a fresh temporary copy every time, so the fixture content and the
self-test's own end-to-end check stay anchored to the same evidence.

## The fixtures

- `all-green`: every one of the fourteen stages passes. `check` exits 0,
  verdict `PASS`.
- `gate-missing-8`: `gates/8.json` was never written. `check` exits 1 and
  names stage 8 and `gates/8.json`.
- `gate-red-9`: `gates/9.json` is present but exited 1 (a real red-green
  failure, not a missing file).
- `gate-unverified-10`: `gates/10.json` is present but exited 2
  (`NOT_APPLICABLE`, no pytest command discovered). `check` reports it as
  UNVERIFIED and blocks.
- `head-drift`: the whole run is built at one commit, then the repository
  advances to a second commit, so every gate file's own recorded `head`
  is now stale. Never overridable.
- `chain-broken`: an early receipt's `detail` is mutated after the fact
  without recomputing its hash, so `gate_state.verify_chain` reports the
  chain broken. Never overridable.
- `block-receipt`: a `block` receipt is appended after an otherwise green
  run. Never overridable.
- `gate-timeout-receipt`: a `gate-timeout` receipt is appended; this alone
  makes `gate_state.verify_chain` report the chain broken, so this
  fixture exercises the same code path as `chain-broken` for a different
  underlying reason.
- `no-approval`: every gate file is green but the `approval` receipt was
  never appended, so stage 6 cannot open.
- `override-covers-9`: the same red `gates/9.json` as `gate-red-9`, plus
  an `override` receipt naming gate `"9"`. `check` exits 0 with verdict
  `PASS_WITH_OVERRIDE`, and the instruction text
  `"override-covers-9 instruction text"` is verbatim in `gates/14.json`.
- `override-cannot-cover-chain`: an early receipt is corrupted the same
  way as `chain-broken`, and an `override` receipt is also present. The
  override does not help; `check` still exits 1.
- `ci-mirror-argv-differs`: `gates/8.json` and `gates/7-discover.json`
  both exit 0 on their own, but their `commands` argv lists differ
  (`pytest -v` was actually run locally while CI discovered `pytest -q`).
  Only stage 13's own computed row fails.
- `stage-query-allowed` / `stage-query-blocked`: built only through stage
  7 (stages 8 to 12 are never written, since a query for stage 8 never
  looks at stage 8's own gate). The blocked variant omits `gates/7.json`.
  `ship_gate.py stage 8 --repo-root <repo>` is run directly against these,
  never `check`.
- `no-run`: a plain git repository with no run ever started against it
  (no `.team-ship/RUN`). Both `check` and `stage` exit 2.
- `receipts-malformed-line`: one `receipts.jsonl` line is replaced with
  text that is not valid JSON at all. `gate_state.verify_chain`'s own
  per-line parsing catches this directly while classifying the chain, so
  `check` never reaches ship_gate's own second read of `receipts.jsonl`;
  it exits 1 with "chain broken" in the reason, not ship_gate's exit 2.
- `override-covers-approval`: no `approval` receipt was ever appended,
  but an `override` receipt names gate `"approval"`. `check` exits 0 with
  verdict `PASS_WITH_OVERRIDE`, and the instruction text
  `"override-covers-approval instruction text"` is verbatim in
  `gates/14.json`. An override is a stronger human act than the approval
  it stands in for.
- `check-from-subdirectory`: an otherwise all-green run, but built with an
  extra empty `sub/` directory inside the repository. `check` is run with
  `--repo-root <repo>/sub`, not `<repo>` itself, and still exits 0,
  because `gate_state.find_run()` walks up from the subdirectory to the
  same `.team-ship/RUN` pointer, and every path resolved afterward
  (EVIDENCE.json, EVIDENCE.md, HEAD) uses run.json's own `repo_root`
  rather than the `--repo-root` argument.

No dedicated fixture exists for `gate_state.derive_status` reporting
`"blocked"` on its own. The only record kind that makes `derive_status`
return `"blocked"` is `gate-timeout`, and `gate_state.verify_chain`
already classifies any receipt of that kind as a broken chain by its own
rule, before `derive_status` is ever consulted. Every case this
generator can construct that reaches `"blocked"` therefore already
reaches `"broken"` first; `gate-timeout-receipt` above exercises both
paths at once (its output carries both "chain broken: gate-timeout: ..."
and "run status blocked: gate-timeout"). Calling `derive_status` and
checking its own "blocked" status regardless is still worth doing, as a
second, independent path to the same conclusion in case a future
receipt kind ever makes them diverge.

## Self-test isolation

`ship_gate.py --self-test` copies every fixture into a fresh temporary
directory before running `check` or `stage` against the copy. `check`
writes `gates/14.json` and appends a receipt, so running it directly
against the checked-in `_build` fixtures would mutate them on every test
run; copying first is what keeps `_build` byte-identical across repeated
self-test runs, the same reason `check_artifacts.py`'s and
`run_gate.py`'s own self-tests copy their fixtures before invoking their
CLIs.
