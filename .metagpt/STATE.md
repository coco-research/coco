## Stage 3, architecture (written, awaiting the gate)

`.metagpt/arch.md` and `.metagpt/arch-diagram.html` are written. The gate value stays
`arch: in_progress` until the owner approves.

What the architecture says, in one line: the loop is a skill that runs a cycle, not a
service, and a model is allowed to write at exactly one stage, into a proposal file that a
guard then refuses unless scope, caps, citation resolution and count coupling all hold.

Decisions worth remembering:

- One model write per cycle, at `propose.py`. observe, validate, open and record are
  deterministic Python, so they are testable without the network or a model.
- One branch and one pull request per cycle, never main, never a merge. The owner's answer
  to Q4 is the reason this is a design invariant rather than a setting.
- The ledger and the signal extracts are committed artifacts, because they have to travel;
  run state stays under the team-gate run directory and is never committed.
- The scheduled workflow runs `--dry-run` only, so no model credentials live in GitHub.
  The real cycle runs where credentials exist, which is honest about the constraint rather
  than pretending CI can be unattended.
- Personas enter at `validate.py` through `build_personas.py` in archetype sized batches.
  They do not fork the pipeline and they do not get their own gate.
- Every new fixture must be hermetic, because this session's two red CI runs both passed on
  macOS and failed on Linux.

The diagram is one architecture view, nine nodes, two accent stages (where the model writes,
and where its output is checked), electric blue on white with glass surfaces and no shadows
per the owner's standing palette preference. It passes the diagram-design skill's own
`self_check.py` and renders offline, since the remote font links were removed in favour of
local stacks.
